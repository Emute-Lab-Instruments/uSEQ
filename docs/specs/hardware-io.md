# Hardware I/O

> Spec: physical pin assignments, input sampling, output writing, LED
> feedback, and boot LED sequences for every hardware variant.  Normative —
> where the implementation disagrees, the implementation is the bug.
> Counterpart to [firmware.md](firmware.md) (composition and tick loop) and
> [inputs.md](inputs.md) / [outputs.md](outputs.md) (language-level leaves
> and sinks).

### Source Files

- `uSEQ/src/firmware/hardware_io.{h,cpp}` — `HardwareIO` struct, all pin maps, `init()`, `read_inputs()`, `write_outputs()`, `update_leds()`, boot LED sequences
- `uSEQ/src/firmware/utils/piopwm.h` — PIO-based PWM program for LED outputs (auto-generated by pioasm)
- `uSEQ/src/firmware/utils/ResponsiveAnalogRead.{h,cpp}` — adaptive-threshold analog smoothing (Music Thing variant)
- `platformio.ini` — variant selection via build environments and `-D` flags

## 3. Input Sampling

All inputs are sampled once per tick in `read_inputs()`, before the signal
engine executes.  Values are stored in `HardwareIO::inputs[MAX_HW_INPUTS]`
(doubles, normalised to `[0, 1]` unless noted).

### 3.1 Input Index Convention

Indices are fixed across all variants.  Unused slots on a given variant
hold 0.0.

| Index | Name | Type |
|---|---|---|
| 0 | INP_I1 | Digital gate |
| 1 | INP_I2 | Digital gate |
| 2 | INP_M1 | Momentary switch |
| 3 | INP_M2 | Momentary switch |
| 4 | INP_T1 | Toggle switch |
| 5 | INP_T2 | Toggle switch |
| 6 | INP_RS1 | Encoder switch |
| 7 | INP_R1 | Encoder position (accumulates) |
| 8 | INP_AI1 | Analog CV |
| 9 | INP_AI2 | Analog CV |
| 10 | INP_MAINKNOB | Knob (Music Thing) |
| 11 | INP_XKNOB | Knob (Music Thing) |
| 12 | INP_YKNOB | Knob (Music Thing) |
| 13 | INP_ZSWITCH | Switch (Music Thing) |
| 14 | INP_AUDIO_L | Audio in (Music Thing) |
| 15 | INP_AUDIO_R | Audio in (Music Thing) |

### 3.2 Digital Gate Inputs (v1.0)

Gate inputs on USEQHARDWARE_1_0 are **interrupt-driven**.  ISR functions
attached via `attachInterrupt(..., CHANGE)` capture the pin state on every
edge and update volatile state variables.  A **rising-edge latch** ensures
short pulses are not missed between ticks:

1. ISR fires on pin change → reads pin, stores to `s_gateN_state`.
2. If the new state is HIGH, sets `s_gateN_latched = 1`.
3. `read_inputs()` reads the volatile state; if the latch is set, reports
   1.0 and clears the latch.

The ISR also drives the gate input LED (`LED_I1`/`LED_I2`) via `digitalWrite`
for instant visual feedback with zero main-loop latency.

The rising-edge latch is a new addition.  The original production firmware
used interrupt-driven reads and ISR-driven LEDs (same as now), but wrote
the pin state directly to the input array without latching — a short pulse
that arrived and departed between ticks could be missed by the main loop
(though the ISR still processed it for external clock tracking).  The
original ISR also called `update_clock_from_external()` on rising edges
when the clock source was set to external; in the current firmware, tempo
estimation is handled separately.

On other variants, gate inputs are polled via `digitalRead` in `read_inputs()`.

### 3.3 Toggle Switch (v1.0, 3-way)

Read from two pins (T1 leg A and T1 leg B), both active-low with pull-ups:

| Leg A | Leg B | Value |
|---|---|---|
| 0 | 0 | 1.0 (center) |
| 1 | — | 2.0 (upper) |
| 0 | 1 | 0.0 (lower) |

### 3.4 Momentary Switch

`1.0 - digitalRead(pin)` — active-low with pull-up.  0.0 = released, 1.0 = pressed.

### 3.5 Analog CV Inputs (v1.0)

- ADC resolution: 11-bit (0–2047).
- Normalisation: `raw * (1.0 / 2048.0)` → `[0, 1)`.
- Filtering: **median-of-51** filter operating on normalised doubles.
  Fixed-size circular buffer (51 elements), partial sort via
  `std::nth_element` per tick.  Same window size as the original
  production firmware.  The original used `std::vector` with heap
  allocation; the current implementation uses a fixed-size stack array.
  On startup, the buffer fills progressively (median of `n` available
  samples) rather than the original's all-zeros initialisation — this
  eliminates the brief 0-biased transient the original had.

### 3.6 Analog Inputs (Music Thing)

- ADC resolution: 12-bit (0–4095).
- Mux-based: 4 channels via 2-bit address lines, 8 µs settle delay.
- 4x oversampling: each mux channel read is averaged over 4 ADC samples
  with 1 µs inter-sample delay.
- Filtering: `ResponsiveAnalogRead` per channel (adaptive-threshold
  smoothing with noise gating and activity detection).
- Normalisation: `value * (1.0 / 4096.0)` → `[0, 1)`.
- CV inputs (mux ch 4–5) are inverted: `4095 - raw`.

### 3.7 Rotary Encoder (v0.2)

Quadrature decoding via a 4-bit state table.  The encoder position
(`INP_R1`) is an accumulating counter — it increases/decreases without
bound.  The encoder switch (`INP_RS1`) is a simple active-low digital
read.

## 4. Output Writing

`write_outputs()` iterates over `HardwareIO::outputs[]`, which the tick
loop fills from the signal engine's output values before calling this
method.

### 4.1 Continuous Outputs

1. Clamp value to `[0, 1]`.
2. Scale to PWM range: `(int)(val * 2047.0)`, clamped to `[0, 2047]`.
3. If `INVERT_ANALOG` (Music Thing only): `2047 - scaled`.
4. Write output pin via `analogWrite(pin, scaled)`.
5. For Music Thing aL/aR (indices 0–1): write via MCP4822 SPI DAC instead
   (12-bit, scaled from 11-bit range).

### 4.2 Continuous Output LEDs

LED brightness follows the output value with an **exponential (squared)
curve** for perceptually linear brightness:

```
led_val = (scaled * scaled) >> 11
```

On standard hardware (v1.0, v0.2), continuous output LEDs are driven by
**PIO state machines** (one per LED, 11-bit period).  On Music Thing and
Expander, they use `analogWrite`.

The `set_output_led()` helper routes correctly based on variant and LED
index, preventing conflicts between PIO and analogWrite on the same pin.

### 4.3 Binary Outputs

1. Threshold: `val > 0.0` → 1, else 0.
2. If `INVERT_DIGITAL` (Music Thing only): flip the bit.
3. Write via `digitalWrite(pin, dv)`.
4. LED: proportional brightness via `analogWrite(led_pin, (int)(val * 2047))`.

Note: the original production firmware used `digitalWrite(led_pin, val > 0)`
for binary output LEDs (simple on/off).  The current proportional brightness
is a deliberate improvement — it shows signal strength on binary LEDs.

### 4.4 Serial Outputs

Indices beyond the physical output count are virtual.  They are not
written to hardware pins; the serial protocol streams them over USB.  See
[wire-protocol.md](wire-protocol.md).

## 5. LED Feedback System

The module provides real-time visual feedback through multiple LED
subsystems.

### 5.1 Output LEDs (all variants)

One LED per physical output.  Continuous output LEDs show signal level
with an exponential brightness curve.  Binary output LEDs show
proportional brightness.  All output LED pins are configured with
`OUTPUT_2MA` drive strength and `GPIO_SLEW_RATE_SLOW` to reduce EMI.

### 5.2 Gate Input LEDs (v1.0)

LED_I1 (pin 5) and LED_I2 (pin 4) are driven directly by the gate input
ISR via `digitalWrite`.  They reflect the physical pin state with
effectively zero latency — no main-loop involvement.

### 5.3 Analog Input LED — AI1 (v1.0, PDM)

LED_AI1 (pin 25) is driven by a **Pulse Density Modulation** timer
running on a 150 µs hardware repeating timer (`add_repeating_timer_us`),
independent of the main tick loop.

Each tick, `read_inputs()` computes a squared+normalised duty cycle from
the raw ADC value:

```
ai1_sq = (raw * raw) >> 11      // squared, 0–2047
pdm_w  = ai1_sq / 2048.0        // normalised, 0.0–1.0
```

The timer callback runs the PDM algorithm:

```
pdm_y   = pdm_w > pdm_err ? 1 : 0
pdm_err = pdm_y - pdm_w + pdm_err
digitalWrite(LED_AI1, pdm_y)
```

This produces smooth, dithered brightness that is visually distinct from
PWM and runs at a consistent rate regardless of main-loop timing.

### 5.4 Analog Input LED — AI2 (v1.0, PWM)

LED_AI2 (pin 24) uses straightforward `analogWrite` with a squared curve:

```
ai2_sq = (raw * raw) >> 11
analogWrite(LED_AI2, ai2_sq)
```

Updated once per tick in `read_inputs()`.

## 6. Boot LED Sequence

The boot LED animation is the module's visual confirmation that it has
powered up and initialised successfully.  It runs after `io.init()`
completes (pins and PIO are already configured) and before the rest of
the firmware init sequence.

In the original production firmware, the animation ran *before* PIO
setup, so all LEDs were driven via `digitalWrite`.  In the current
firmware, PIO is initialised in `init()` before the animation runs, so
output LEDs must be driven through the PIO-aware `set_output_led()`
helper.  The visual result is identical.

### 6.1 USEQHARDWARE_1_0

A sequential LED chase cycling through all 12 indicator LEDs:

**Pattern:** AI1 → AI2 → A1 → A2 → A3 → D3 → D2 → D1 → I2 → I1

Each LED turns on while the LED two steps behind turns off, creating a
moving window of 2 lit LEDs.  The animation runs 8 iterations with
decreasing inter-step delay (30 ms → 6 ms), producing an accelerating
sweep.

Output LEDs (A1–A3, D1–D3) are driven via `set_output_led()` which uses
PIO PWM for continuous LEDs and `analogWrite` for binary LEDs.  Input
LEDs (AI1, AI2, I1, I2) are driven via `digitalWrite`.

### 6.2 USEQHARDWARE_0_2

Same principle — sequential chase through I1 → A1 → D1 → D3 → D4 →
D2 → A2 → I2.  8 iterations, delay decreasing from 30 ms.

### 6.3 Other Variants

Fallback: all output LEDs at 50% brightness (amber glow).

### 6.4 Ready Signal (new)

After the full firmware init sequence completes (engine, flash, I2C,
devtools), `boot_led_green()` turns all output LEDs off and blinks the
onboard LED (LED_BUILTIN) for 50 ms to signal readiness.  The original
production firmware had no explicit ready signal — it went straight from
the animation into the main loop.

### 6.5 Error Flash (new)

`boot_led_error_flash()` — 3 rapid blinks of all output LEDs at full
brightness (80 ms on / 80 ms off).  Used when flash load fails during
boot.  No equivalent in the original production firmware.

## 7. PIO PWM

Standard hardware variants (v1.0, v0.2) use the RP2040's Programmable I/O
(PIO) state machines to drive continuous output LEDs.  This frees the
hardware PWM peripherals for the output pins themselves.

- PIO program: loaded from `pwm_program` (auto-generated by pioasm in
  `utils/piopwm.h`).
- `pio0` state machines 0–3 handle up to 4 continuous LEDs.
- `pio1` handles overflow (> 4 continuous LEDs, currently unused).
- Period: `(1 << 11) - 1` = 2047 (11-bit).
- Level set via `pio_sm_put_blocking`.

Music Thing and Expander variants use `analogWrite` for all LEDs instead
of PIO (different pin constraints).

## 8. Feature Flags

Hardware I/O behaviour is gated by compile-time feature flags passed as
`-D` defines in `platformio.ini`:

| Flag | Controls |
|---|---|
| `ENABLE_LED_CONTROL` | All LED init and feedback |
| `ENABLE_ANALOG_INPUTS` | ADC config, analog input reading, AI LED feedback |
| `ENABLE_DIGITAL_IO` | Gate input pin modes, interrupts, binary output writing |
| `ENABLE_ENCODER_INPUT` | Rotary encoder (v0.2 only) |

When a flag is absent, the corresponding hardware is not initialised and
the corresponding code paths are compiled out.

## 9. Differences from Original Production Firmware

The current hardware IO implementation matches the original production
firmware (`uSEQ.cpp` in the pre-rewrite codebase) in all pin assignments,
filtering algorithms, LED drive methods, and boot animation patterns.
The following are deliberate improvements:

| Area | Original | Current | Rationale |
|---|---|---|---|
| Analog filter allocation | `std::vector` (heap) | Fixed-size stack array | No heap on embedded hot path |
| Analog filter startup | All-zeros, biased until filled | Progressive fill (median of N available) | Eliminates 0-bias transient |
| Gate input latch | ISR writes state directly; main loop can miss short pulses | Rising-edge latch; main loop sees every pulse for ≥1 tick | Prevents missed triggers |
| Gate ISR clock tracking | ISR called `update_clock_from_external()` on rising edges | Tempo estimation handled separately | Architectural separation |
| Binary output LEDs | `digitalWrite` (on/off) | `analogWrite` (proportional brightness) | Shows signal strength |
| Boot LED PIO awareness | Animation ran before PIO init; used `digitalWrite` everywhere | Animation runs after PIO init; uses `set_output_led()` for PIO-owned pins | Correct peripheral routing |
| Boot ready signal | None — straight to main loop | `boot_led_green()` blinks onboard LED | Explicit readiness indicator |
| Boot error flash | None | `boot_led_error_flash()` — 3 rapid blinks | Flash load failure feedback |
| `pdm_w` volatility | Not declared `volatile` (latent bug) | Declared `volatile` | Correct cross-context access |
