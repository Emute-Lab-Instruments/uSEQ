# Audit Bloat Report — 2026-05-04

**Mode**: default (tiered) | **Agents**: 4 (3 completed, 1 stalled — cross-cutting gaps filled manually) | **Scope**: full firmware sweep

## Summary

The codebase carries **~10,000 lines of dead old-architecture code** (`uSEQ/src/uSEQ/`, `uSEQ/src/dsp/`, `uSEQ/src/io/`) excluded from all builds but still on disk. The new `firmware/` + `signal_engine/` architecture is clean and well-structured, but has accumulated phantom NodeOps, duplicate eval logic, legacy test-only API overloads, and a WASM wrapper with significant internal duplication. CLAUDE.md is severely stale — its key file references describe the old interpreter architecture that no longer exists.

### [Severity: high] — Triplicated eval logic across executor and node_pool

- **Location**: `signal_engine/executor.cpp:14-129` (runtime `eval_node`), `signal_engine/node_pool.cpp:10-71` (constant-folding `eval_unary`/`eval_binop`/`eval_ternary`)
- **Anti-pattern**: Duplicate code paths
- **What exists**: Every mathematical operation is implemented twice: once in the per-sample hot-path dispatcher and again in the constant-folding path. Both are switch statements over the same `NodeOp` enum. They've already drifted: `eval_unary` handles `HashIndex` but omits `USinBi`/`UCosBi`; `eval_node` handles all three.
- **What it should be**: A single `eval_op(NodeOp, double, double, double)` static inline function used by both paths. The hot path still handles load ops separately.
- **Confidence**: high
- **Effort to fix**: medium (must not regress hot-path performance)
- **Embedded cost**: ~2.5KB flash for duplicate switch tables

### [Severity: high] — Legacy eval_cold() and on_cell_changed() overloads with heap-allocating shim

- **Location**: `signal_engine/cold_eval.cpp:771-822` (legacy `eval_cold`), `cold_eval.cpp:957-993` (legacy `on_cell_changed`), `cold_eval.h:75-76,93-95,100-101`
- **Anti-pattern**: Duplicate code paths / over-abstracted wrapper
- **What exists**: Legacy overloads take separate `CellStore&, SourceArena&, NodePool&` args. The legacy `eval_cold` heap-allocates a `SignalEngine` (`new SignalEngine()`), does 20+ memcpy operations to transfer state in/out. Only used by ~49 test callsites in `test_signal_engine.cpp`. All newer tests and all production code use `SignalEngine` directly.
- **What it should be**: Delete legacy overloads, `g_engine_state`, and `output_sources[]` globals. Migrate test callsites to `SignalEngine`.
- **Confidence**: high
- **Effort to fix**: medium (bulk test refactoring)
- **Embedded cost**: ~1.5KB flash + ~7KB RAM for globals (`output_sources[42]` + `g_engine_state`)

### [Severity: medium] — WASM wrapper has 3 near-identical batch eval functions (~350 duplicated lines)

- **Location**: `wasm/wasm_wrapper.cpp` — `useq_eval_outputs_time_window` (lines 771-898, returns JSON), `useq_eval_outputs_time_window_into` (lines 900-1013, writes to buffer), `useq_tick_and_project` (lines 1061-1183, tick + projection)
- **Anti-pattern**: Duplicate code paths
- **What exists**: All three functions duplicate: JSON output-name parsing, output index resolution, time array construction, active-output row mapping, batch execution dispatch (the same 3-way `has_active_state()` / `batch_workspace` / `sequential` branch), and per-channel result copying. The only differences are output format (JSON string vs buffer write) and whether projection is involved.
- **What it should be**: A shared `prepare_batch_eval()` helper that does parsing, index resolution, time array build, and batch execution. Each export function calls it and handles its own output format.
- **Confidence**: high
- **Effort to fix**: medium
- **Embedded cost**: ~3KB WASM binary for duplicated logic

### [Severity: medium] — WASM wrapper has 4 hand-rolled JSON parsers

- **Location**: `wasm/wasm_wrapper.cpp` — `useq_set_live_inputs` (lines 458-511, hand-rolled object walker), `useq_apply_state_snapshot` (lines 564-668 helpers + 670+, separate hand-rolled parser), plus `parse_output_names` and the serial_protocol parsers
- **Anti-pattern**: Duplicate code paths
- **What exists**: At least 3 independent JSON parsing implementations: one for `useq_set_live_inputs`, one for `useq_apply_state_snapshot` (with its own `skip_json_string`/`skip_json_value`/`find_field_at_depth`/`extract_json_string`/`extract_json_number` helpers — ~100 lines), and the output name parser. The firmware's `serial_protocol.cpp` has yet another JSON parser with `find_field_value`/`extract_string`/`extract_int`.
- **What it should be**: A single minimal JSON walker shared across the WASM wrapper and firmware. The `serial_protocol.cpp` pattern (`find_field_value`) is actually decent — extend it rather than reinventing.
- **Confidence**: medium (each parser handles slightly different shapes, but the core walking logic is the same)
- **Effort to fix**: medium

## Clean Areas

- **Signal engine node pool + CSE** (`node_pool.h/cpp`) — Hash-consing, algebraic simplifications, zero-allocation. Exactly right for embedded.
- **Executor hot path** (`executor.cpp:133-170`) — Lean, no allocations, linear scan. `ExecutionContext` is clean.
- **Token/TokenStream** (`token.h/cpp`) — Fixed-size, zero-alloc, 16-byte tokens. Clean except for the broken quote handler.
- **Cell store** (`cell_store.h/cpp`) — Flat array, 16-byte cells, clean data table pool.
- **Form dispatch table** (`graph_builder.cpp:31-108`) — Binary-searched, X-macro initialized. Good extensibility pattern.
- **UGen implementations** — All follow consistent pattern, map cleanly to specs.
- **Diagnostics** (`diagnostics.h/cpp`) — Static-string-only, no heap. Fuzzy matching is appropriate.
- **Firmware composition root** (`firmware/firmware.h/cpp`) — Clean tick loop, sensible module ownership.
- **Serial protocol** (`firmware/serial_protocol.h/cpp`) — Zero-alloc JSON parsing, proper ring buffer.
- **Flash storage** (`firmware/flash_storage.h/cpp`) — Properly-used port abstraction with `IStorage`/`MockStorage`.
- **symbols.def X-macro** — Data-driven, single source of truth, well-categorized.
